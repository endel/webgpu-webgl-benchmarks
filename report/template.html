WebGPU Engine Bench

Nine key tests for choosing a 3D engine for the web, built identically in each engine and measured frame by frame on WebGPU and WebGL2. Every scene renders the same geometry, lights and camera at 1920×1080 with 4× MSAA and ACES tone mapping; the harness owns the frame loop and times each engine through the same instrumentation.

Does the promised feature work?

Each test, path and backend either rendered a verified frame, is not applicable because the engine has no such feature, or failed. Two marks per browser: WebGPU, then WebGL2.

    Same engine, different browsers

    CPU time per frame for each engine in each browser, at one fixed level per test, current backend and path. CPU time is the one metric every browser reports identically: Safari caps the frame rate at the display refresh.

    How each engine drives the GPU

    WebGPU calls per frame recorded by the harness's probe (not the engine's own counters) for 1,000 animated meshes in a hierarchy, plus live GPU memory from every buffer and texture the engine allocated.

    Startup and footprint

    Shipped JavaScript (tree-shaken, minified, brotli) for the smallest lit-cube app and for a realistic one (glTF, animation, shadows, bloom), and the time from navigation to the first rendered frame.

    Bundle size

    Brotli-compressed, every chunk the build emits. Engines that load shaders or features on demand (Babylon.js, Babylon Lite, PixiJS 3D) download only part of this.

    Time to first frame

    Did they render the same thing?

    Frame 60 of each scene in Chrome on WebGPU, captured by the harness. Identical data in, so any visible difference is the engine's lighting model or defaults.

    API friction

    Lines of TypeScript each adapter needed to build the same nine tests, by file. Fewer lines for the same result means less to write and maintain; a missing file means the engine had no path for that test.
